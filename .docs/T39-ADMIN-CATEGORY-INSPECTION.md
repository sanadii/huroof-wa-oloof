# T39 — Admin category inspection and correction (2026-09-24)

## Authority and verified baseline

The user requested category view/edit and a way to inspect every question in a category, including question/answer text and media, difficulty, and related information on `/admin/categories`. This is authorized implementation work, following the existing admin design and immutable-release architecture. The current list links only to a short category detail; published questions are in a separate filtered, paginated server query. Published category/question records are immutable. `adminCategoryMetadata` is a separate authoring collection, and production admin mutations are staged. No published question in the captured T38 release has a `difficulty` property; the UI must say that honestly. Existing media preview is verified and capped at 1 MB.

**Decision T39.D1:** Edits are correction drafts for review and a successor immutable release, never in-place writes to an active release. The user was asked whether edits should be immediate or reviewed; no answer arrived during the independent inspection milestone, so the reviewed model is the stated working assumption and can be adjusted if the user replies. The database review is complete. Do not label an `adminCategoryMetadata` save as a player-visible change.

**Visual contract:** Reuse the existing admin surfaces: calm Arabic cobalt/navy/ice, IBM Plex Arabic, density 5/10 desktop and 4/10 mobile. The category title and question count lead, followed by actions and a compact paginated list; detail opens a readable question/answer/media surface. Maintain 8/16/24/32 spacing, semantic status and focus states, existing `admin-*` components, and restrained motion. Avoid giant cards, raw release JSON, invented difficulty, and exposing private storage paths.

### T39.2 — Category correction entry

**Resolved scope:** An administrator with `categories.write` can edit the proposed Arabic category name and an internal correction note as a **draft**, explicitly showing the published name beside it. The draft binds category ID, current release ID/root hash, baseline label, author, revision, operation ID, and status. Each save retains an immutable revision snapshot and audit record; stale revision, changed active release, wrong role/scope, and replay mismatch fail closed. This milestone implements draft saves only. Review and publication controls remain unavailable until a separate policy and frozen-revision workflow are defined; no direct published catalog write or game-read override is allowed. Production write enablement uses a dedicated correction-draft gate and session capability indicator; it never turns on global admin mutations. The shared draft is one record per category and base release, protected by optimistic revision checks. Only super_admin or a category-scoped content_admin may read its internal note or edit it. Publication to players remains the existing successor-release workflow and requires a fresh-base verified plan and separate activation action; the editing page must say this plainly.

**Database impact and rollback:** Additive `adminCategoryCorrections` records/revisions only; no migration, Firestore Rules change, or active release pointer change. If the draft feature fails, disable its specific callable gate and retain audit/history. The database review also identified a catalog-prefix audit gap in the general release adapter; a future category publication must fix and exercise that path before activation. No category change is published as part of this feature unless a separately reviewed successor release is actually prepared and verified.

**Owner:** Forge after root resolves edit semantics with user and database review; root acceptance. **State:** Authorized, pending implementation under decision T39.D1. **Scope:** Provide a clearly labelled correction form for proposed Arabic category title and internal correction note only, with revision/conflict handling, audit and role checks.
